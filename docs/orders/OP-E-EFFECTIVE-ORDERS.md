# Effective order management (bounded PAPER implementation)

This slice reduces a funded, active ATOMIC Spot fixed-limit entry from its current total quantity to a smaller total quantity. The original price, client ID, venue ID and FIFO queue priority remain unchanged. Original accepted terms, original creation hashes and all financial reservations remain unchanged. Existing CANCEL behavior continues through the same public management boundary.

## Interfaces

- `ProgramManagementService.admit(original_command_id, ManagementInstruction(kind=KEEP_PRIORITY, new_quantity=...), lease)` reads the actual venue target outside the business transaction and retains current authorization, owner/fence, account cash, funding and cause checks. The instruction must satisfy `cumulative < new total < current total`; nonpositive quantities, list children, protective/reduce-only orders, iceberg orders, STP variants and nonfixed prices are excluded from this initial runtime slice.
- `ManagementBoundary.mark_may_have_sent/consume/recheck_consumed` and `submit_management` retain the existing private single-use permit, private cross-database consumed authorization, execution-owner guard, actual market advisory lock and order row lock. Current business facts and the original SIM authorization are rechecked after both waits and before commit. Creation TTL does not terminate management duty; the fresh management permit still expires.
- `PaperManagementTargetReader.capture` continues to consume `engine.query_creation`. For an amended order that query returns `PaperManagedCreationReportV1`, never an unchanged ordinary V2 report. Its distinct tag/source is `PAPER_MANAGED_CREATION_REPORT_V1` / `PAPER_MANAGED_CREATION_SOURCE_V1`, version `2026-10-30.managed-v1`.
- `ManagedCreationCodecV1.encode/decode` validates the exact closed fields, revision, tag and evidence hash. Decoding a source DTO does not authorize execution or establish provenance. The actual reader authenticates immutable overlays through protected SIM authorization and receipt tables.
- `observe_effective_management(service, command_id)` queries the original creation ID independently, authenticates the exact management receipt in its effective history, and records only that action's applied resolution. It returns the versioned receipt. It is also the recovery path after a lost ACK; it never retries submission, obtains another permit, releases funds, marks the order FLAT, or closes protection/late-fill duties.

`OwnedTargetSnapshot.original_quantity` is the venue's current total order quantity used by the existing compiler (the venue's amended origQty), while immutable original size is retained in accepted terms and explicitly in each overlay. The managed report makes all four quantities available: original accepted size, effective total, cumulative actual fills, and current leaves. For a 1.0 order filled by 0.2 and amended to total 0.5, these are 1.0, 0.5, 0.2 and 0.3. The evidence hash excludes observation time, so a later unchanged query does not invent a new economic revision.

## Official semantics and deliberately bounded behavior

Public Spot documentation checked 2026-10-30: [Order amend keep priority](https://developers.binance.com/en/docs/catalog/core-trading-spot-trading/api/rest-api/trade). It specifies positive new quantity below current quantity and permits retaining the current client order ID by explicitly sending it as `newClientOrderId`. The compiler now does that. The existing stronger guard requiring the new total to exceed cumulative fills remains; this implementation does not infer undocumented below-cumulative behavior. Native endpoint support for linked lists is not proof of this application's sibling/protection admission, so that capability remains a separate follow-up.

Unqualified follow-ups: list amendments, price MODIFY, cancel-replace, protected/reduce-only action proofs, STP/iceberg amend semantics, static financial-source registration, reconciler accounting ingestion of the new source, and executable host enabling. The new report does not impersonate the ordinary V2 financial source and does not automatically register itself. This is isolated PAPER qualification only; no LIVE/TESTNET, account activation or signed endpoint access was performed.

## Review fix: independent applied-source authority (0029)

Apply `0029_effective_management_source.sql` to BUSINESS after 0027 and the existing 0016 source-verifier role setup. 0027/0028 bytes and all old resolution/history rows remain unchanged. A legacy resolution row alone now has no effect on admission. Admission requires the new immutable confirmation joined to its committed immutable source attestation. A fresh attestation can safely confirm an action even when an unsafe legacy row occupies the old primary key; that old payload and xmin are preserved.

The independently trusted `ledger_program_source_verifier` authority may execute `attest_effective_management_source_v1`; dispatch/owner/control/decision roles cannot. No runtime role memberships or source grants are automatically installed for dispatch principals. The source function checks the complete managed report/tag/hash, scoped original identity, exact management binding/receipt in effective history and committed BUSINESS consumption hash. The actual source reader establishes SIM provenance before calling this function. This is a separate credential trust boundary, not a claim that hashes authenticate caller-supplied DTOs.

`ProgramManagementService(..., source_uow=...)` now takes an explicitly composed, separately credentialed source UnitOfWork. `observe_effective_management` queries actual SIM, validates the closed managed codec, commits source attestation through this UoW, and only then calls the dispatch resolver in another transaction. Missing source composition fails closed. The resolver requires an exact matching committed source attestation; known IDs, a source tag or BUSINESS consumption alone are insufficient. Fresh dispatch permits/current guards, no-release semantics and original duties remain unchanged. Repeated exact observation is idempotent; a later changed actual source may append another immutable attestation but cannot duplicate the action or confirmation.
