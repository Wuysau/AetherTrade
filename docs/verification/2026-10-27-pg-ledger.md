# Isolated PostgreSQL ledger repair evidence

Scope: reservation reconciliation, durable dispatch fixtures, and persistent risk
lock resolution. Base `3062154`; this evidence does not qualify venue/native/LIVE
execution or complete the wider PAPER acceptance task.

**Security follow-up:** Independent review found that the original audit-only
unsent abort did not block the base permit port or direct owner SQL. The repair
and expanded 190-test actual PostgreSQL evidence are recorded in
[the authoritative abort follow-up](2026-10-27-command-abort-guard.md).

## Findings and changes

The 20 reservation baseline failures started in a stale fixture that directly
appended terminal states to immutable command rows. The production reconciliation
reader also ignored IP-10 audit-backed outcomes. Fixtures now exercise real durable
send-boundary/outcome methods, and reconciliation uses the effective command
repository. An explicit mutex-serialized unsent abort retires a ready command;
MAY_HAVE_SENT, UNKNOWN, and confirmed commands cannot be relabeled unsent. The
legacy NOT_SENT fixture case uses that explicit abort, without claiming transport
or venue evidence.

Three resolution failures exposed a real missing implementation: Python evidence
verification attempted a raw RESOLVED insert that the database correctly rejected.
Additive migration `0002_risk_resolution_authority.sql` supplies a separately
privileged resolution function and private transaction-bound approvals. The service
requires both its existing authoritative verifier and an explicitly supplied
resolver UoW. Ordinary execution-owner rights cannot mint approvals, invoke the
function, impersonate the resolver, or bypass the guard using forged audit rows or
custom settings. Failure before/after projection writes rolls back the event,
approval, projection, and audit together.

One dispatch fixture tried to mutate the intentionally immutable active-owner
registry. It now asserts that mutation is rejected and simulates a stale owner at
the domain binding gate. New actions fail; identical enqueues retrieve the original
UNKNOWN outcome and do not send again. This is not proof of an implemented database
ownership-transfer CAS; that remains a separate requirement.

## Actual test run

The source worktree was bound read-only to a dedicated `python:3.12-slim` Docker
runner, copied inside that container for Python installation and bytecode, and
connected only to the parent's isolated PostgreSQL 17 qualification cluster.
Synthetic DSNs are in ignored `.runtime/linux-pg-ledger.env`; no credentials are
included here. The final test databases were fresh before fixture installation:

- `ip07_test_pgledger_final_9529ab27`
- `ip08_test_pgledger_final_9529ab27`
- `ip10_test_pgledger_final_9529ab27`

Linux command inside the dedicated runner (after normalizing the Windows env file
to LF and exporting it):

```sh
cd /tmp/app
python -m pytest -q tests/integration/test_reservations.py tests/integration/test_persistent_risk_locks.py tests/integration/test_durable_dispatch.py --junitxml=/evidence/ledger-final.xml
```

Result: **147 passed in 19.16s; exit 0; zero skips**. Raw artifacts:
`.runtime/ledger-final.log`, `.runtime/ledger-final.xml`, `.runtime/ledger-final.exit`.
The initial run also passed all 147 cases in 19.89s. An intermediate invocation
sourced CRLF environment values incorrectly and skipped database tests; it was
rejected as evidence and corrected before the final fresh-database run above.

`git diff --check` and Python compilation of all changed Python files also passed.

`ledger_owner` current role with `rolsuper=false`, and enabled command, lock, and
owner guards in all three databases. The risk database additionally proves:

| Privilege | Value |
| --- | --- |

A separate regression creates an actual non-superuser login with only
`ledger_owner` membership, authenticates as that login, and verifies denial of
resolver role assumption, resolution execution, and private approval insertion.
The login is removed after the test; no password appears in test output.
